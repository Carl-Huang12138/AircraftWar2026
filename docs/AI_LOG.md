## 实验二：代码迁移（从 Windows 到 Android：让飞机大战跑起来）

### 问题 2.1：桌面端图片资源迁移到 Android（规避 AAPT 资源大小写报错与 OOM 隐患）
* **遇到什么问题**：  
  原 Java Swing 项目中的图片资源存在驼峰命名（如 `elitePlus.png`、`prop_bulletPlus.png`），且原 `ImageManager` 使用 `java.awt.image.BufferedImage` 和 `ImageIO.read()` 加载。直接复制进 Android 会报非法资源命名错误，且桌面端图像 API 无法在 Android 运行。
* **AI建议**：  
  ① Android `res/drawable` 资源命名必须严格为纯小写字母、数字和下划线，需全部重命名为小写 snake_case（如 `elite_plus.png`）；  
  ② 必须改用 Android 原生的 `android.graphics.Bitmap` 和 `BitmapFactory.decodeResource()`；  
  ③ 必须在初始化阶段一次性 decode 缓存至静态 Map，严禁在绘制循环中反复加载，防止发生内存溢出（OOM）。
* **进行的修改**：  
  将 19 张图片规范化小写重命名后导入 `app/src/main/res/drawable/`；将 `AbstractFlyingObject` 中的图像类型改为 `Bitmap`；重构 `ImageManager.java`，编写 `initImage(Context context)` 配合 HashMap 实现安全的预加载与全局静态缓存。

### 问题 2.2：游戏主循环迁移与屏幕分辨率自适应（SurfaceView 双缓冲机制）
* **遇到什么问题**：  
  原项目基于 Swing 的 `JPanel.paint(Graphics g)` 和 `java.util.Timer`，需要迁移为 Android 的 `SurfaceView`，并解决不同手机屏幕分辨率不一致导致的画面偏位与黑屏问题。
* **AI建议**：  
  ① 继承 `SurfaceView` 并实现 `SurfaceHolder.Callback` 与 `Runnable`，在子线程中使用 `lockCanvas` → 绘制 → `unlockCanvasAndPost` 实现 60fps 双缓冲渲染；  
  ② 在 `surfaceChanged` 中读取手机真实屏幕宽度与高度，动态更新 `Main.WINDOW_WIDTH` 与 `WINDOW_HEIGHT`，使英雄机与背景按真实分辨率等比适配；  
  ③ 在 `surfaceDestroyed` 中妥善结束绘制子线程，防止 Activity 销毁后后台仍在刷屏造成内存泄漏。
* **进行的修改**：  
  新建 `BaseGame.java`（SurfaceView 循环基类）与 `EasyGame.java`；实现背景双图滚动拼缝算法；在 `MainActivity.java` 中直接设置 `setContentView(new EasyGame(this))`，成功在真机/模拟器上渲染出平滑滚动的星空背景与居中的英雄机。

### 问题 2.3：触屏交互适配与游戏逻辑闭环（连击 Combo 机制还原）
* **遇到什么问题**：  
  原项目使用鼠标拖动控制战机，需改为手指触屏拖拽；同时需要将子弹射击、敌机批量生成、碰撞判定、道具掉落及连续击杀 Combo 机制接入新的主循环。
* **AI建议**：  
  ① 重写 `BaseGame` 的 `onTouchEvent`，监听 `ACTION_DOWN` 和 `ACTION_MOVE`，并对战机位置添加 `[width/2, screenWidth - width/2]` 严格边界防出界限制；  
  ② 在游戏主循环 `action()` 中顺序组织：连击超时检测、敌机生成周期、敌我射击周期、子弹/敌机/道具移动、碰撞检测（`crashCheckAction`）与失效对象清理（`removeIf`）；  
  ③ 还原原项目中 2 秒内连续击杀判定机制，在 Canvas 上动态渲染橘黄色 `COMBO xN !!` 连击特效字体及最高 5 倍的得分计算。
* **进行的修改**：  
  在 `BaseGame.java` 中完整实现了触屏控制与所有碰撞、掉落、计分逻辑；当英雄机生命归零时在屏幕中央渲染 `GAME OVER` 提示，完成了实验二要求的“画得出来、动得起来、碰得准确”全部闭环。

## 实验三：界面交互与音效系统

> 本次接力账号：Xu-Jiyun-xuan。以下记录 Codex 在本地执行的修改与自动化模拟器验证，不代表成员已经亲自试玩、试听或提交。

### 问题 3.1：实验二直接进入 EasyGame，缺少菜单和其他难度
* **遇到什么问题**：MainActivity 直接加载 EasyGame；Android 工程未包含普通和困难场景。
* **AI建议**：使用 XML 布局、监听事件和 Intent extra 传递难度与音效开关；复用桌面版的难度模板与图片。
* **进行的修改**：新增 MenuActivity、Difficulty、MediumGame、HardGame，将菜单设为启动页；MainActivity 依参数选择场景，未知参数回退简单；补齐返回菜单和屏幕系统栏适配。

### 问题 3.2：子线程不能弹窗，后台及重开需要清理场次状态
* **遇到什么问题**：游戏结束原来只在 Canvas 显示文字；Surface/Activity 生命周期可能重复启动循环；重开和系统重建需要区别处理。
* **AI建议**：游戏线程发送 Message，主线程 Handler 统一处理结算；以锁和线程身份检查控制一次循环；生命周期停止游戏，并在销毁时清理消息。
* **进行的修改**：新增 GameEvent，生命归零仅发送一次得分；主线程显示结算并支持重开/返回；系统重建保留结果，主动重开清空；暂停后时间不再推进。补上机身碰撞不依赖子弹、失效子弹不重复命中及敌机难度血量不被补血上限截断的回归检查。

### 问题 3.3：原桌面音频 API 不适用 Android，Boss 音乐需互斥切换
* **遇到什么问题**：Android 尚无音频管理；普通曲目与 Boss 曲目需要暂停/恢复，并在后台与销毁时管理资源。
* **AI建议**：独立 GameAudioManager 持有 Application Context；MediaPlayer 管长音乐，SoundPool 管四类短音效；全部音频调用由主线程处理。
* **进行的修改**：从原项目复制六个 WAV 至 res/raw；实现开关、循环、互斥切换、加载完成回调、前后台暂停和幂等释放。独立审查指出初版切换会重新开始普通音乐，新增回归先得到失败，再改为保留两条曲目的暂停位置。

### 问题 3.4：验证必须包含真实设备状态和可复现结果
* **遇到什么问题**：离线缓存缺少 Gradle 设备测试宿主组件；Espresso 默认根窗口在结算弹窗出现时可能选错；原 local.properties 路径未转义导致 Lint 错误。
* **AI建议**：用 ADB 安装既有测试 APK 并直接运行 AndroidJUnitRunner；弹窗测试明确使用 isDialog()；修正本机 SDK 属性转义。
* **进行的修改**：单元测试 4/4、模拟器设备测试 11/11 通过，APK 构建与 Lint 通过（Lint 保留警告）；保留真实截图、失败到通过的音频回归记录及最终日志。详细说明见 [EXPERIMENT3.md](EXPERIMENT3.md)。没有自动推送、合并或课程提交。

### 问题 3.5：用户试玩反馈连射慢、敌弹速度随难度变化
* **遇到什么问题**：英雄发射间隔原为600/800/880ms，直射子弹仅5像素/帧；敌方部分射击策略叠加飞机速度，Boss环射又独立使用较低速度。
* **AI建议**：把英雄射击节奏与难度解耦，集中定义射速参数；子弹仅使用自身固定速度，保留难度间的敌机发射频率差异，所有弹道按标称速度计算分量。
* **进行的修改**：新增 CombatTuning；英雄统一120ms连射、30像素/帧弹速；敌方统一14像素/帧标称弹速，保留直射/双排/散射/环射。去除困难递进中的英雄减速。新增测试先失败后通过；最终6项单元测试、12项模拟器测试和Lint通过（39条警告），第二版已安装到模拟器，首版APK保留。

---

### 问题 3.6：用户指定普通射击参数，并保留初版道具弹幕
* **遇到什么问题**：第二版把普通和道具射击统一提速，用户要求普通英雄弹速24、敌弹12、英雄每240ms发射一次，道具保持最初射速和弹速。
* **AI建议**：普通射击仍集中配置；根据当前射击策略判断是否为道具模式，使用独立的初版道具周期，恢复原散射和环射的速度分量。
* **进行的修改**：普通模式调整为6逻辑帧、弹速24；敌弹12；散射恢复(±2,-5)，环射恢复8及初版分量取整；道具周期恢复简单15、普通20、困难初始22帧及原递进规则，结束后回到普通6帧。策略字段使用volatile以便游戏循环看见原道具计时线程的模式切换，第三版APK单独保留。

---

### 问题 3.7：用户反馈首局卡顿、结算后重开持续无声、下半屏抖动
* **遇到什么问题**：实际绘制后固定休眠使目标25帧/秒仅达到约15帧/秒；早期重开测试关闭了声音，未覆盖音频和结算页生命周期组合。
* **AI建议**：先增加带声音的连续重开、音乐循环和帧预算测量；按剩余预算休眠，每帧完整清屏；新一局复用音频资源并显式重置。独立复核补查后台与系统重建后的结算页。
* **进行的修改**：硬件绘制试验的帧预算测试曾通过，但完整场景切换出现阻塞，已撤回硬件绘制；保留计时修正，超预算也短暂休眠避免占锁，等待Surface尺寸后完整重画背景并缓存缩放结果。用户授权冷启动模拟器后，最终软件方案首局/重开后实测约24.4帧/秒，7项单元测试、19项模拟器测试全部通过（93.659秒），构建与Lint通过（0错误、39条警告）。重开替换游戏并清理旧消息，保留音频资源；新增两项结算页生命周期测试复现音频前台状态未恢复，修正后通过。没有稳定复现用户原始直接重开的完全无声；播放状态测试不能代替人工试听，录屏抽帧不能证明所有抖动消失。第四版成果单独保存，待用户复测。

### 问题 3.8：背景接缝经过底部时出现错层
* **遇到什么问题**：用户指出底线附近每隔数秒出现交错/上移，要求不再花时间复现。代码将非无缝背景的顶边与底边直接拼接，存在明确的画面断层。
* **AI建议**：纵向镜像重复使拼接两侧使用同一边缘；镜像周期按两倍图高计算，取模保留余量；按屏幕像素绘制背景。
* **进行的修改**：新增ScrollingBackground集中管理缓存、MIRROR采样与位移，BaseGame调用它绘制背景。构建、7项单元测试和Lint通过；新增3项离屏像素检查已编译，但当前模拟器未运行，未执行设备测试。未启动模拟器重现实时抖动，原背景素材及射击/音频参数保持不变；第五版APK单独保存。

### 问题 3.9：困难Boss过强，三连发需要追平普通射击
* **遇到什么问题**：用户要求适度降低困难Boss血量和弹幕密度，但仍高于普通；三连发射速与弹速改为当前普通英雄机水平。
* **AI建议**：困难Boss血量增量减半，使用独立固定发射计时；仅环射继续用原道具发射周期，三连发使用普通6帧周期与24标称弹速。
* **进行的修改**：困难Boss首只800降至650，后续每次加150（原300），普通仍500；困难Boss固定760ms/轮，普通800ms/轮，均20发，其他敌机节奏不变。三连发每240ms一轮，标称弹速24，保持原散射夹角，环射未改。三连发弹速单元回归先失败后通过，最终8项单元测试、构建与Lint通过。用户要求安装试运行后，已安装第六版并完整通过23项模拟器测试（95.676秒），覆盖Boss数值、三连发周期和背景像素接缝；通过ADB实际进入困难模式、拖动射击、结算重开并返回菜单，保留截图与录屏。没有人工试听或自然游玩到Boss的声明。第六版成果单独保存。
